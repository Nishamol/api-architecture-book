# Chapter 19: Schema Evolution and Backward Compatibility — Solutions

*Corresponds to: [part5-cross-cutting/19a-schema-evolution-compatibility-exercises.md](../../part5-cross-cutting/19a-schema-evolution-compatibility-exercises.md)*

## Concept questions — Model answers

1. Protobuf's wire format encodes fields by their numeric tag, not by their name — the tag is what's actually written to the bytes on the wire, and the field name exists only in the `.proto` source and the generated code. So renaming a field in the `.proto` file (keeping the same tag) doesn't change a single byte of what's transmitted between two services that both regenerate their stubs from the updated file — the wire format itself is indifferent to the rename. What breaks is anything whose correctness depends on the *name* specifically rather than the tag: the chapter's example is `grpc-gateway`, which generates a JSON mapping from the `.proto` definition — that JSON mapping uses field names as JSON keys, so a rename changes the JSON key a REST-via-transcoding client sees, breaking any consumer of that generated REST API even though the underlying gRPC wire format never broke.

2. If a field is defined as an enum and a new value is added on the producer side (e.g., an `OrderStatus` enum gains a new `PARTIALLY_REFUNDED` value), any consumer still running old generated code that doesn't know about that new value will decode it as the enum's zero value by proto3's default behavior — not as an error, not as a visibly "unknown" state, but silently as whatever value is defined at position zero (often something like `UNSPECIFIED` or, worse, a semantically meaningful default like `PENDING`). A client displaying order status or making a business decision based on it could silently treat a `PARTIALLY_REFUNDED` order as `PENDING` (or whatever the zero value is) with no error raised anywhere — a silent misinterpretation rather than a loud failure, which is exactly why the chapter flags this as something to be deliberate about rather than assume is safe just because it's "handled."

3. A structural compatibility check (like the rules for safe vs. breaking changes) evaluates a schema change in the abstract — does it remove a field, tighten nullability, change a type — without any knowledge of who is actually using what. This flags every structurally breaking change as breaking, including ones where, in practice, no real client currently queries the affected field. A schema-diffing tool run against real production query logs can distinguish between a change that's "technically breaking" (violates the structural rules) but affects zero actual traffic, versus one that's breaking *and* would actually break requests currently being sent by real clients. The former can often ship safely (or with much less caution); the latter genuinely can't. A purely structural check can't make this distinction and will flag both identically, producing noise that either gets ignored over time or blocks changes that are actually safe in practice.

4. The first failure mode is unnecessary version proliferation for GraphQL or Protobuf: an engineer assumes, by analogy to REST, that any change needs a new version, and bumps a version (or forks a schema) for a change that GraphQL's or Protobuf's own rules would have allowed as purely additive — a nullable field addition, a new enum value, a new `.proto` field with a new tag — none of which needed a version bump at all under that protocol's actual compatibility rules. The second, more dangerous failure mode is a genuinely breaking change shipped because someone assumed a change was safe "by analogy to a different protocol's rules" — for instance, assuming a Protobuf field rename is as harmless as a REST field rename typically is treated (informally), without realizing that even though the *wire format* tolerates the rename, dependent tooling like `grpc-gateway` does not. The two failure modes are opposite in effect — one is excess caution/overhead, the other is insufficient caution/an outage — but both stem from applying REST's loose, version-based mental model to a protocol with its own, different, tag- or schema-based rules.

5. Protobuf diffs the `.proto` file itself, checking field tags and types against the previously committed schema, via `buf breaking`. GraphQL diffs the SDL, via GraphQL Inspector or Apollo's schema checks — optionally strengthened by checking against real production query logs. REST diffs the OpenAPI YAML/JSON document, via tools like `openapi-diff` or Optic. The three artifacts and tools differ because each protocol expresses its contract differently — a compiled schema definition, a hand- or tool-authored SDL, and a spec document, respectively — so there's no single tool that could diff all three the same way. But the goal is identical across all three: catch a breaking change mechanically, in CI, before it ships to a consumer, rather than relying on a human reviewer to notice a breaking diff by reading it — which is precisely the discipline the chapter's next section (“The core discipline across all three protocols”) generalizes into one principle regardless of protocol.

## Design question — Model answer

**(1) Removing `line_item_count` (tag 4) and reusing tag 4 for `total_amount_cents`:** this is the chapter's canonical breaking change — "reusing a tag number for a different field or type." Any client still running old generated code that reads tag 4 as `int32 line_item_count` will now decode the bytes of the new `int64 total_amount_cents` field as if they were the old field, producing garbage or a wrong value with no error raised. "It's unused" doesn't make this safe, because "unused" refers to whether current first-party code calls it — it says nothing about every consumer with an already-deployed binary built against the old `.proto`, which is exactly the population this chapter's rules are designed to protect. The safe migration: mark tag `4` (and the name `line_item_count`) `reserved` so it can never be reused, and give `total_amount_cents` a brand-new tag number (e.g., `5`).

**(2) `Order.discountCode` nullable → non-nullable:** the chapter lists this explicitly as breaking — "changing a field from nullable to non-nullable... existing clients not sending that field, or backends not always populating it, now fail." "It's always populated now" is a claim about the current data, not a guarantee about every code path, past and future, that produces an `Order` — a rarely hit branch (an edge-case order type, a legacy import path, a partial failure elsewhere in the resolver graph) that doesn't set `discountCode` will now cause a hard validation failure for any client that previously tolerated `null` there, instead of just seeing `null` as before. The safe migration: leave the field nullable, and if the goal is to communicate to consumers that it's now reliably populated, do that through documentation, monitoring/telemetry proving it's consistently non-null in practice, and — if a genuinely non-nullable variant is wanted — introduce a *new* field (or a schema-registry-tracked deprecation cycle per the chapter's core discipline) rather than tightening the existing one in place.

**CI enforcement:** `buf breaking` in CI against every `.proto` change, checking against the previously committed schema, would have caught the tag reuse mechanically before merge. On the GraphQL side, a schema-diffing tool (GraphQL Inspector or Apollo's schema checks) run in CI — ideally checked against real production query logs, per the chapter — would have flagged the nullable-to-non-nullable change as breaking, and would have shown whether `discountCode` is a field real client queries currently rely on being nullable. Both checks should be required, not optional, exactly because — as the chapter puts it — this is "cheap to automate and expensive to skip."

## Coding exercise — Model answer

```protobuf
message Order {
  string id = 1;
  string status = 2;
  reserved 3;                  // previously "customer_email", removed — never reuse tag 3
  reserved "customer_email";
  reserved 4;                  // previously "line_item_count", removed — never reuse tag 4
  reserved "line_item_count";
  int64 total_amount_cents = 5;
}
```

If tag `4` had instead been deleted and directly reassigned to `total_amount_cents` without `reserved`, an old client still running code generated from the previous `.proto` version would still be sending or expecting tag `4` to mean `int32 line_item_count`. When it receives a message where the server (running the new `.proto`) has populated tag `4` with an `int64 total_amount_cents` value, the old client's deserializer decodes those same bytes as if they were the old field's type and meaning — at best producing a nonsensical number in `line_item_count`, at worst (given the different wire types between varint-encoded `int32` and `int64`) causing a decoding mismatch. Either way, it's a silent data-corruption bug on the old client's side rather than a clean, visible failure — precisely the risk that `reserved` exists to eliminate by making the tag permanently unusable.
