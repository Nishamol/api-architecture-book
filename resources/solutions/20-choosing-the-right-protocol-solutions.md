# Chapter 20: Choosing the Right Protocol — Solutions

*Corresponds to: [part6-synthesis/20a-choosing-the-right-protocol-exercises.md](../../part6-synthesis/20a-choosing-the-right-protocol-exercises.md)*

## Concept questions — Model answers

1. The four axes are: (1) who the client is and how many client teams exist, (2) what the access pattern looks like, (3) the team's tolerance for operational complexity, and (4) the caching story. For the first axis, the chapter's contrast is direct: a public API has "unknown, unbounded consumers," and "you cannot coordinate a schema migration with clients you don't have a relationship with" — which pushes toward REST's loose, self-describing contract precisely because nothing tighter can be safely coordinated at that scale of unknown consumers. A small number of first-party mobile/web teams, by contrast, "can tolerate GraphQL's tighter coupling to a shared schema, because you can actually coordinate changes with them" — the same underlying question (how many clients, how coordinated) produces the opposite conclusion because the coordination cost is the deciding variable, not some inherent property of "being a client."

2. REST and GraphQL both have a design that inherently risks over/under-fetching (REST because the server decides the response shape and the client is stuck with it either too large or too small; GraphQL because it lets the client specify the shape, which is how it "solves" the same problem REST has). gRPC doesn't confront this axis at all in the same terms — its unit of communication is a typed RPC call whose request and response shapes are whatever the `.proto` contract defines for that specific call, so the concept of "the client wanted a different subset of fields than the server sent" doesn't really apply the same way; you'd define a different, narrower RPC if you needed a different shape. It's "N/A" rather than "solved" because gRPC's contract model sidesteps the question by fixing the shape per call at design time, rather than providing a mechanism (like GraphQL's field selection) for the client to negotiate it at request time.

3. The chapter identifies the more specific mistake as applying one protocol's operating model to a context it wasn't designed for — not simply picking a protocol that turns out to be suboptimal, but taking a protocol whose entire design assumes a certain relationship with its consumers (internal, trusted, coordinated) and exposing it to a fundamentally different consumer population it was never built to serve. Exposing raw internal gRPC services directly to third-party integrators illustrates this: gRPC's whole value proposition (compile-time contract coupling, no coordination overhead because you control both ends) inverts into a liability the moment the consumer is an external third party you can't coordinate with — you've forced Protobuf/HTTP2 tooling onto people who have no reason to adopt it. A public GraphQL API without cost-limiting and federation discipline illustrates the same underlying mistake from the other direction: GraphQL's flexibility model assumes a bounded, cooperative client population, and exposing that same flexibility to arbitrary, diverse public traffic (per Chapter 9) turns the query graph into an availability risk, because nothing about GraphQL inherently protects a server from an unbounded, uncooperative consumer constructing an expensive query.

4. REST's caching is close to free because its contract is URL-keyed and stateless by convention — a `GET` to a specific URL returns a specific representation, and every caching layer in the stack (browser, CDN, reverse proxy) already knows how to key a cache entry off a URL and standard HTTP cache headers, with zero GraphQL- or gRPC-specific logic required. GraphQL's contract is the opposite: every request goes to a single endpoint, and the same URL can return wildly different response shapes depending on the query body sent — there's no URL-level key that uniquely identifies "this specific response," so generic HTTP-layer caching has nothing to key off, and you need either normalized caching on the client (understanding the graph's entities independent of any one query) or persisted-query IDs on the server (giving a stable key to an otherwise-variable request) to get caching at all.

## Design question — Model answer

- **Own web app and mobile apps → GraphQL.** These are first-party client teams the company can coordinate schema changes with, and per the chapter's access-pattern axis, first-party UIs commonly need differently-shaped subsets of the same data per screen — exactly GraphQL's sweet spot, and exactly the situation where its tighter coupling is affordable because coordination is possible.
- **~40 third-party integration partners → REST**, kept as (or migrated to) the existing REST surface, ideally generated via gRPC-JSON transcoding off a shared `.proto` definition once internal services move to gRPC, so the REST contract and internal contract can't drift apart silently. Third parties are exactly the "unknown, unbounded" (well, bounded but uncoordinated) consumer population the chapter says needs REST's loose, self-describing, universally-tooled contract — you can't push Protobuf or GraphQL query-cost discipline onto 40 external companies' engineering teams.
- **New internal service-to-service calls → gRPC**, for any newly built internal communication paths, since the company controls both ends and can take on compile-time contract coupling without external coordination risk, per the "who is the client" axis.

**Highest-risk mistake for this company:** the raw-gRPC-to-third-party mistake is the more likely one here, specifically *because* they already have 40 integration partners relying on today's REST API. If the migration team, in the process of introducing gRPC internally, is tempted to "simplify" by exposing the new internal gRPC services directly to save the work of maintaining a separate REST surface, that would immediately break (or force a forced-migration burden onto) all 40 existing partners, who have no relationship to Protobuf/HTTP2 tooling and were never asked to adopt it. The existing REST surface is a sunk commitment to a specific, loose contract with an uncoordinated consumer population — exactly the situation the chapter warns is incompatible with gRPC's assumptions — so the path of least resistance during a careless migration (reuse the new gRPC contract everywhere, including externally) is precisely the mistake the chapter calls out.

## Applied exercise — Model answer

**1. New row — "Coordinating a breaking schema/contract change with consumers":**

| Concern | REST | GraphQL | gRPC |
|---|---|---|---|
| Coordinating a breaking change | Hardest in practice — unknown/diverse consumers means you version the URI (`/v1`, `/v2`) and run both indefinitely, since you can't force anyone to migrate | Moderate — a small, known set of first-party client teams means you can coordinate directly, but Chapter 19's `@deprecated` discipline and query-log-driven schema diffing are still required to avoid surprising them | Easiest for consumers you control — compile-time contract coupling means a breaking `.proto` change is caught immediately for internal consumers at build time, but the same tight coupling makes it risky for any consumer outside your coordination reach |

This grounds directly in the chapter's "who is the client" axis: REST's difficulty coordinating a breaking change is a direct consequence of having "unknown, unbounded consumers" you have no relationship with, so URI versioning (running old and new in parallel) is close to the only option. GraphQL's moderate difficulty follows from having "a small number of first-party client teams you can actually coordinate with" — coordination is possible, but Chapter 19 still requires deliberate tooling (schema diffing against real query logs) rather than assuming coordination alone is sufficient. gRPC's ease-for-controlled-consumers/risk-for-outside-consumers split follows directly from the "you control both ends" assumption baked into its whole design — that assumption holds for internal consumers and fails for anyone outside it.

**2. Challenging the "Streaming" row's GraphQL cell:**

"Subscriptions (heavier-weight)" compresses a real tradeoff into three words. GraphQL subscriptions typically run over WebSockets or SSE, require the server to hold open connections and push updates per-subscriber, and don't give you gRPC's four native RPC shapes (unary, server-streaming, client-streaming, bidirectional) — a GraphQL server has to bolt subscription infrastructure on as a separate mechanism from its query/mutation execution model, rather than streaming being a first-class transport-level capability the way it is in HTTP/2-based gRPC. A team would reasonably choose gRPC streaming over GraphQL subscriptions even for an otherwise-GraphQL-appropriate first-party client population when: the streaming workload is high-frequency/low-latency (e.g., live order-tracking updates at sub-second intervals, not occasional notification pushes), when bidirectional streaming is needed (a GraphQL subscription is fundamentally server-to-client push, not a two-way stream), or when the streaming endpoint sits behind an existing internal gRPC service mesh and adding a second, GraphQL-specific streaming transport would duplicate connection management, backpressure, and mTLS work the gRPC layer already handles. In that case, a first-party client might reasonably call a narrow gRPC-streaming endpoint directly (or through a thin proxy) for that one high-frequency feature, while still using GraphQL for everything else — the axes support a hybrid decision at the level of a single feature, not just at the level of "which protocol for this client population."

## Quiz (self-check) — Answers

1. **False.** The chapter explicitly says "hybrid architectures are the norm, not the exception" and that "very few real production systems pick exactly one protocol for everything" — the recommended pattern is gRPC internally, GraphQL for first-party clients, and REST for third parties, not standardization on one protocol.
2. **"Who is the client, and how many client teams exist?"** — this axis determines whether schema/contract changes can be coordinated directly with consumers or must be treated as uncoordinatable.
3. **REST** — the chapter calls it "the lowest common denominator," noting that "every engineer, every tool, every debugging technique from the last 25 years works against it with no translation layer."
4. **They combine protocols in a hybrid architecture**: gRPC between internal services, a GraphQL BFF/federated graph for first-party clients, and a REST API (often generated via gRPC-JSON transcoding) for third-party integrators and webhook consumers.
