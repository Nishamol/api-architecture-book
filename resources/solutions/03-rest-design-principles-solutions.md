# Chapter 3: REST API Design Principles — Solutions

*Corresponds to: [part2-rest/03a-rest-design-principles-exercises.md](../../part2-rest/03a-rest-design-principles-exercises.md)*

## Concept questions — Model answers

1. A URL is supposed to name a resource (a noun), and the HTTP method is supposed to carry the intent (the verb) applied to that noun. `POST /orders/42/cancel` keeps that split intact — the resource is still `/orders/42`, and `cancel` is a genuine business action that doesn't map to CRUD, so it's modeled as a sub-resource. Burying the same intent inside `PATCH /orders/42` with a `{"status": "cancelled"}` payload instead moves the actual meaning of the request out of the URL and method and into an opaque data field the server has to inspect and branch on. Any HTTP-aware infrastructure — logging, caching, monitoring dashboards, API gateways doing method-based routing — can see and reason about `POST .../cancel` without opening the body; none of them can distinguish "set status to cancelled" from any other `PATCH` without parsing the payload. It also weakens the idempotency contract: `PATCH` is not guaranteed idempotent in the same well-understood way, and business logic hidden in payload fields is easy to extend sloppily (e.g., a `status` field that silently accepts values nobody intended, like `"refunded"`, without the explicit review a new endpoint would get).

2. Level 1 just means the API has moved past a single tunnel endpoint and has multiple resource URIs (`/orders`, `/customers`) — but everything might still go through, say, `POST` regardless of the operation. Level 2 additionally means HTTP verbs and status codes are used correctly and meaningfully: `GET` for reads, `POST` for creation, `PATCH`/`PUT` for updates, `DELETE` for removal, with status codes reflecting real outcomes. That's the level where HTTP's built-in tooling (caching, retries, gateways, monitoring) actually works as intended, which is why the chapter calls it "a perfectly reasonable place to stop." Level 3 (HATEOAS) earns its complexity in APIs where the client genuinely needs to discover valid next actions at runtime rather than having them hardcoded — the chapter names workflow engines and public banking APIs operating under regulatory hypermedia requirements as examples, where the set of valid transitions from a given state can change independently of client releases.

3. `POST /orders` creates a resource, and by default HTTP gives no guarantee that calling it twice produces the same result — two identical `POST` calls can create two orders. Mobile clients frequently retry requests after a timeout or a dropped connection without knowing whether the original request actually succeeded server-side, which means a naive `POST /orders` retried after a flaky connection can silently create a duplicate order (and, worse, duplicate a charge if payment is tied to order creation). The idempotency-key pattern in the chapter closes this gap by having the client generate a stable key per logical operation and send it as a header; the server checks whether it has already processed that key and, if so, returns the previously computed result instead of re-executing the side effect. This effectively makes `POST` behave idempotently *for that specific operation*, without changing HTTP's general rule that `POST` isn't idempotent by default.

4. Offset pagination identifies "where the next page starts" purely by position — "skip the first 100 rows, give me the next 20" — which only means something stable if the underlying ordering and row set don't change between page requests. Under concurrent writes, a row inserted before the current offset shifts every subsequent row's position by one, so the next page either re-shows a row already seen (if a row was deleted before the offset) or skips one entirely (if a row was inserted before the offset) — the "page" boundary is really just "an index into a set that's still changing." Cursor pagination instead identifies "where the next page starts" by a stable pointer — a cursor derived from a specific row's identity (e.g., its primary key or a monotonic sort key), like the chapter's `?cursor=eyJpZCI6NDJ9`. Because the cursor points at an actual row rather than a shifting numeric position, inserts and deletes elsewhere in the table don't change what "the row after this cursor" means, so pages stay consistent even while the table is being written to concurrently.

5. The allowlist prevents two distinct failure modes at once. First, a performance one: it keeps "sortable/filterable" in sync with "actually has a database index" — a field that isn't indexed doesn't error, it just gets slow under production data volume in a way that's invisible in development with a handful of test rows, so the allowlist is what stops a client from ever reaching an unindexed column at all. Second, a security one: if a field name were passed straight into a query builder or raw SQL without validation, an arbitrary client-supplied string reaching that code path is an injection risk. "The client asked for this exact field name" isn't sufficient justification because the client's request is exactly the untrusted input the allowlist exists to constrain — a real column name isn't automatically a safe or performant one to sort or filter by, and only the allowlist's author (not the caller) can know which fields are actually indexed and safe to expose this way.

## Design question — Model answer

**Violation 1 — `POST /api?action=cancelOrder&id=42`.** This is textbook action-as-noun leakage: a single tunnel endpoint dispatching on a query parameter, which is Richardson Maturity Model **Level 0/1** behavior (RPC-over-HTTP dressed as a URL), not resource-oriented REST. Fix: `POST /orders/42/cancel` — a proper action sub-resource under the `/orders/42` resource, exactly the pattern the chapter explicitly endorses as an escape hatch for non-CRUD operations.

**Violation 2 — `PUT /orders/42` incrementing `version` unconditionally.** `PUT` is defined as idempotent — calling it N times must have the same effect as calling it once. Incrementing a counter on every call regardless of whether the payload changed breaks that contract outright: a client or gateway that retries a `PUT` after a timeout (standard, expected behavior for an idempotent method) will silently increment `version` multiple times for what should be a single logical update. Fix: make the handler compare the incoming payload against current state and only bump `version` (or write anything) if something actually changed; two calls with the same payload must leave the resource in the same state either way.

**Violation 3 — every response returns `200`, success/failure in the body.** This collapses the status-code layer entirely, which the chapter calls a "surprisingly common anti-pattern" that "breaks every layer of standard HTTP tooling." Fix: return real status codes — `201` on order creation, `404` if the order doesn't exist, `409` for a conflict (e.g. optimistic-concurrency failure), `422` for validation failures, `200` only for genuine success — so CDNs, service meshes, and client retry libraries can key off the status code the way they're designed to, instead of every caller having to parse the body to know if a request failed.

**Violation 4 — `GET /orders` unpaginated.** This has no explicit pagination strategy, which the chapter flags as something that must be decided "from day one" because retrofitting it later is a breaking change once clients depend on getting the full collection back. Fix: add cursor-based pagination now, before external integrators build against the unpaginated shape — cursor-based specifically, since order tables are exactly the kind of high-write-volume collection where offset pagination would drift under concurrent inserts.

**This API is currently at Richardson Maturity Model Level 0/1** — the cancel action is tunneled through a single endpoint dispatching on a parameter, and even the resources that do have their own URIs (`/orders/42`) don't reliably use HTTP verbs and status codes to carry meaning (the flattened `200`-everywhere pattern). It hasn't reached Level 2 yet, let alone Level 3.

**Why these must ship before third-party integrators are let in:** every one of these problems becomes a breaking-change migration once external consumers depend on the current (broken) behavior. Third parties will build retry logic against whatever status-code behavior they observe; if that's "always 200," fixing it later means every integrator's error handling breaks simultaneously. Third parties will build clients against the unpaginated `GET /orders` response; adding pagination later is explicitly called out in the chapter as a breaking change once that dependency exists. Fixing these while the only consumers are internal, coordinated teams costs a sprint; fixing them after 200 external integrators have built against the current contract costs a multi-quarter deprecation project — exactly the kind the chapter describes in its "deprecation is a project, not a flag" material for a later chapter on versioning.

## Coding exercise — Model answer

The bug: `db.insert_order(...)` runs unconditionally, before the idempotency check. On a retried `POST /orders` with the same `idempotency_key`, the handler creates a **second** database row every time, even though the second call's *response* happens to look identical to the first because `_seen_keys` correctly returns the cached response body. The client sees a consistent, deduplicated response and has no way to know a duplicate order was actually persisted — which is worse than an obviously broken retry, because it fails silently and only surfaces later (duplicate fulfillment, duplicate charges, an inventory count that doesn't reconcile).

Fix — check the key before writing, and make the check-then-write atomic enough that concurrent retries with the same key can't both pass the check:

```python
@app.post("/orders")
async def create_order(payload: dict, idempotency_key: str = Header(...), db=Depends(get_db)):
    existing = _seen_keys.get(idempotency_key)
    if existing is not None:
        return existing

    order = await db.insert_order({"id": generate_id(), **payload})
    _seen_keys[idempotency_key] = order
    return order
```

This still has a real race window under true concurrency (two requests with the same key both passing the `existing is None` check before either writes to `_seen_keys`), which is exactly why the chapter's own comment says `_seen_keys` should be `Redis/DB in production` — a production fix needs the idempotency-key check-and-set to be an atomic operation against shared storage (e.g., a unique constraint on `idempotency_key` in the orders table, or a Redis `SET ... NX`), not an in-process dict, so two concurrent requests with the same key can't both win the check.
