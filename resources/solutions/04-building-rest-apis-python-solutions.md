# Chapter 4: Building REST APIs in Python — Solutions

## Concept questions — Model answers

1. The chapter says DRF "earns its keep when you need Django's ORM, admin panel, and migrations ecosystem — most commonly when the API sits inside a larger Django monolith rather than as a standalone service." In other words, the deciding factor isn't raw framework capability, it's whether you're building a brand-new, standalone, async-first service (FastAPI's sweet spot) or adding an API surface on top of an existing Django application that already gets real value from Django's admin UI, ORM, and migration tooling. In the latter case, running a second framework alongside Django just to serve the API would mean maintaining two web stacks, two sets of models, and losing the admin panel's ability to inspect and edit the same data the API serves — DRF avoids all of that by living inside the Django app you already have.
2. `response_model=OrderOut` makes FastAPI serialize the return value strictly against the fields declared on `OrderOut`, stripping anything else — so even if the handler returns a raw ORM object or dict carrying internal fields (password hashes, internal IDs, feature flags, cost basis, whatever else lives on the underlying record), only the fields explicitly declared on the output model reach the client. It functions as an allowlist rather than a denylist: you don't have to remember to strip sensitive fields, because anything not explicitly declared is dropped by default. This is precisely the bug the "Missing `response_model`" failure mode names — "internal fields ... leaking into API responses because the handler returned the raw ORM object" — which is the failure state you get when a handler either omits `response_model` or bypasses it by returning a hand-built dict instead of letting FastAPI serialize against the declared model.
3. With a module-level singleton or global DB connection, a test that wants to exercise `create_order` against a fake database has no seam to substitute one — the handler is hard-wired to whatever connection the module happened to establish at import time, so tests either need a real database running (slow, and now integration tests, not unit tests) or resort to monkeypatching module internals (fragile, and easy to leave broken between tests since it doesn't route through a documented API). `Depends(get_db)` avoids this because the dependency is resolved per-request through FastAPI's DI system rather than hard-coded into the handler body; `app.dependency_overrides[get_db] = get_test_db` swaps in `FakeDB()` for every request the `TestClient` makes, with zero changes to `create_order` itself. The handler doesn't know or care whether it's talking to a real pooled connection or an in-memory fake — that's exactly the point of using DI as a testing seam.
4. FastAPI runs each worker's event loop cooperatively: an `async def` handler only yields control back to the event loop at an `await` point, so the event loop can only serve other in-flight requests while the current handler is actually awaiting something (a DB call, a downstream HTTP call). A *synchronous* call inside that handler — like the commented-out `generate_report_sync(report_id)` — doesn't yield at all; it blocks the Python thread the event loop is running on for its entire duration, so every other request assigned to that same worker sits frozen until the synchronous call returns, regardless of what those other requests are doing. The fix shown in the chapter, `await loop.run_in_executor(None, generate_report_sync, report_id)`, moves the blocking call onto a separate thread pool so the event loop itself is only awaiting the executor's future — able to keep serving other requests — rather than being blocked by the synchronous work directly.

## Design question — Model answer

**Incident 1 (p99 latency tripled across every endpoint, not just `/invoices`).** This is the direct consequence of the concurrency model explained in the chapter: the synchronous PDF-generation call inside `async def generate_invoice` blocks the event loop of whichever worker handles that request for the full duration of PDF generation. During that window, that worker can't make progress on any other in-flight request — not just other invoice requests, *any* request routed to that worker, which is exactly why the latency hit shows up on unrelated endpoints. With 8 workers and requests round-robined or randomly distributed across them, roughly 1-in-8 of all requests land on a worker that's periodically frozen by this call, dragging up the aggregate p99 even though most individual requests never touch `/invoices` at all. Fix: wrap the synchronous call in `await loop.run_in_executor(None, generate_pdf_sync, ...)` (or replace the library with an async-native equivalent), exactly as the chapter's `get_report` example demonstrates, so the blocking work runs on a thread pool instead of the event loop thread.

**Incident 2 (DB pool exhausted despite `8 × 15 = 120` looking safe against a 200 limit).** The arithmetic `workers × pool_size` only bounds the *pool's own* connection ceiling — it says nothing about how much of that ceiling gets used concurrently under real traffic, and it says nothing about other consumers of the same database (migrations, cron jobs, other services). More importantly here: while a worker's event loop is blocked by the synchronous PDF call, requests that already acquired a DB connection and are mid-transaction can't release it back to the pool as quickly, and new requests queue up waiting for a connection rather than failing fast — so a traffic spike concentrated on the blocked worker can look like pool exhaustion even when the static `workers × pool_size` math checks out, because concurrency is not evenly distributed the way the multiplication assumes. The fix for the immediate symptom is the same as Incident 1 (unblock the event loop so connections get released promptly), but the pool sizing itself should also be revisited against actual concurrent-in-flight-request counts under load, not just the theoretical `workers × max_concurrent_requests_per_worker` ceiling — which is the exact formula the chapter names as the thing that has to be accounted for, and "accounted for" means validated under realistic load, not just multiplied out on paper.

**Why fixing only the PDF call isn't sufficient on its own:** the blocking call is what's *triggering* the pool exhaustion under current traffic, but the pool was already sized without headroom relative to `workers × max_concurrent_requests_per_worker` — the chapter calls this out as its own distinct failure mode ("Unbounded connection pools"). Even after the event loop is unblocked, a future traffic spike or a different slow endpoint could reproduce the same exhaustion, because the underlying sizing problem — pool capacity not validated against real concurrency, independent of any one handler's bug — was never addressed. Fixing the PDF call removes the trigger; it doesn't remove the latent capacity risk.

## Coding exercise — Model answer

```python
from pydantic import BaseModel
from datetime import datetime

class UserOut(BaseModel):
    id: str
    email: str
    created_at: datetime

@app.get("/users/{user_id}", response_model=UserOut)
async def get_user(user_id: str, db=Depends(get_db)):
    user = await db.get_user(user_id)
    return user
```

Declaring `response_model=UserOut` and only listing `id`, `email`, and `created_at` means FastAPI serializes the return value strictly against `UserOut`'s declared fields, silently dropping anything else the ORM object carries — `password_hash`, `is_admin`, and `feature_flags` never reach the JSON response, because they were never declared as part of the output contract. This is the allowlist property from this chapter's `create_order`/`OrderOut` example: the safety doesn't come from remembering to strip specific dangerous fields (a denylist, which breaks the moment a new sensitive field gets added to the ORM model and nobody updates the strip list), it comes from `UserOut` only ever exposing what's explicitly declared. A future sensitive field added to the `User` ORM model is safe by default under this pattern — it simply won't appear in responses until someone deliberately adds it to `UserOut`.
