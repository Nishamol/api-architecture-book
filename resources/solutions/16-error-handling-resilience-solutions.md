## Concept questions — Model answers

1. Machine-readable `code` values matter because "client code branches on codes, not on message text that might change wording without warning and silently break string-matching error handling." If a client's retry/error logic does something like `if "not found" in response["error"]["message"]`, that logic silently breaks the moment someone rewords the message (e.g., "No order exists with id 42" becomes "Order 42 could not be located") — a change nobody would think of as breaking, because it looks like a copy edit, not an API contract change. Branching on a stable `code` field like `ORDER_NOT_FOUND` avoids this entirely, since the code is part of the explicit contract and isn't expected to change wording-by-wording the way prose is.

2. **Non-idempotent without an idempotency key**: the chapter's example is a payment-charge call. If a client retries a charge after a network blip without an idempotency key, and the original request actually succeeded server-side but the response was lost in transit, the retry creates a second, duplicate charge — "resulting in duplicate charges during exactly the network conditions that make retries tempting," as the failure-modes section puts it. **Permanent failures**: the chapter names `404`, `422`, and gRPC's `INVALID_ARGUMENT` as failures that "will fail identically on every attempt." Retrying a `422` (say, a malformed request body) wastes time and resources on every attempt — since nothing about the request changes between retries, the server will reject it the same way every time, so the retry can only ever delay the client from surfacing the real, non-transient problem to whoever needs to fix it.

3. The jitter defends against synchronized retry storms: "without it, many clients that all failed at the same moment (e.g., during a brief backend blip) retry in lockstep, turning a transient issue into a self-inflicted thundering herd exactly when the backend is recovering." Without the jitter term, every client computing `base_delay * (2 ** attempt)` for the same `attempt` number produces the *exact same delay*, so a population of clients that all failed simultaneously (because they were all hitting the same struggling backend at the same moment) also all retry simultaneously — hitting the recovering backend with a synchronized spike of traffic at precisely the moment it's least able to absorb it, potentially knocking it back down right as it was recovering.

4. After the cooldown period elapses, the breaker is still nominally `OPEN`, but the *next call* triggers the check `time.monotonic() - self.opened_at > self.cooldown_seconds` — since that's now true, the breaker transitions to `HALF_OPEN` and, critically, does *not* raise `CircuitOpenError` for this call; it falls through to actually invoke `fn()`. If that call succeeds, the `except` block never fires, `failure_count` resets to 0, and `state` is set back to `CLOSED` — full recovery, calls flow normally again. If that call fails, the `except` block increments `failure_count`; since the breaker was already at/above `failure_threshold` from before (that's why it opened in the first place), the `if self.failure_count >= self.failure_threshold` check is very likely still true, so `state` is set back to `OPEN` and `opened_at` is reset to now — the breaker immediately starts a fresh cooldown period rather than continuing to let calls through, correctly treating the failed recovery probe as evidence the dependency is still unhealthy.

5. A circuit breaker only stops calling a dependency once it's already been detected as failing — after crossing `failure_threshold`. It does nothing to limit how much of the caller's own capacity (threads, connection-pool slots) that dependency can consume in the meantime, either before the breaker has gathered enough failures to trip, or during calls that are merely slow rather than outright failing. A bulkhead caps that consumption from the very first call: `recommendations_bulkhead`'s 10 slots can never be exceeded no matter how slow or how failure-prone `recommendations` becomes, which means `inventory_bulkhead`'s separate 50 slots are structurally protected regardless of what the breaker has or hasn't detected yet. The chapter calls them "usually deployed together" because they cover different phases of the same problem: the bulkhead limits the blast radius continuously, from the very first slow call, while the circuit breaker — once it does trip after crossing its threshold — cuts off calls to the failing dependency entirely, saving even the bulkhead's capped resources for calls that have some chance of succeeding.

## Design question — Model answer

1. Each hop's 5-second timeout is set with zero knowledge of time already spent by callers *before* it. Worst case: the client calls `orders`, which is genuinely slow to start its own downstream call (say, due to load) and consumes nearly all 5 seconds of its own budget just deciding to call `billing` — but `orders`'s timeout only bounds *its own* wait on `billing`, not the client's wait on `orders`. Concretely, the compounding the chapter describes is additive across hops: `orders` can wait up to 5s on `billing`, and independently, `billing` can wait up to 5s on `payment-gateway` before `billing` gives up and returns an error to `orders` — and `orders`'s own 5s timeout is a *separate* clock that only starts when `orders` calls `billing`, not synchronized with how much of the client's original patience is left. In the chapter's own words: "each hop in a call chain independently timing out at, say, 5 seconds, so a 3-hop chain can take 15 seconds total even though the original caller only waited 5 seconds" — i.e., the caller's actual timeout expectation (5s) has no relationship to what the system, hop by hop, actually allows (up to 15s) because no hop knows what budget it's operating inside of.

2. Deadline propagation means the *original* caller sets one deadline (e.g., "this whole request must complete or fail within 5 seconds from now"), expressed as an absolute point in time, and that deadline — not a fresh, independent timeout — is passed along on every subsequent hop. Concretely: the client calls `orders` with a 5-second deadline; `orders` computes the absolute wall-clock deadline (`now + 5s`) and, when calling `billing`, passes that *same absolute deadline* (not a new 5-second timer) as part of the call (in gRPC, this is native — the deadline set on the outer call is automatically available to propagate to the child call, per Chapter 10). `billing` does the same when calling `payment-gateway`: it computes how much time is actually left before the shared deadline and uses that as its own effective timeout for the `payment-gateway` call, rather than starting a fresh 5 seconds. What has to flow between hops is the absolute deadline itself (or equivalently, "time remaining"), not a fixed per-hop timeout value — every hop reads the same clock, so the total chain can never exceed the original 5-second budget, and a hop with little time left can even fail fast rather than waste the (already-exhausted) time budget dialing a downstream service that has no chance of returning in time.

3. A **circuit breaker** should sit in front of the `billing` call. A deadline alone still lets `orders` dial `billing`, wait out whatever time remains on the deadline, and then fail — that's bounded, but it's not *fast* if `billing` is failing outright (e.g., completely down or erroring on every call) rather than just slow. The chapter's circuit-breaker failure mode is exactly this: "a slow downstream service causing every caller to pile up threads/connections waiting on it, exhausting the caller's own resources and turning one service's slowness into a cascading outage." A circuit breaker in front of `billing` detects the sustained failure rate and, once it crosses the threshold, stops sending requests to `billing` entirely during the cooldown — `orders` fails fast on the next request rather than waiting out its deadline budget on a call that's very likely to fail anyway, which protects both `orders`'s own resources (no threads/connections tied up waiting) and gives `billing` room to recover without more load piling on top of whatever's already wrong.

4. The chapter's graceful-degradation material distinguishes essential response components from best-effort ones: "a well-designed... endpoint should return the order with an empty recommendations section rather than failing the entire response" when a non-essential downstream is unhealthy — but this only applies to parts of the response that are genuinely optional. The "charge card" step via `payment-gateway` is essential — an order can't be considered successfully placed if the charge didn't go through, so a `payment-gateway` failure must become a real, surfaced error to the client (following the chapter's error-envelope guidance, with an appropriate `code` and `retryable` value) rather than being silently degraded. The `recommendations` call, by contrast, is exactly the kind of best-effort, non-critical component the chapter's example describes: if `recommendations` is down, `orders` should catch that failure locally and return the rest of the response (the order itself) with an empty or omitted recommendations section, rather than failing the entire request over a component that was never essential to "did the order succeed." Treating both failures identically — either failing the whole response for a recommendations outage, or silently swallowing a payment failure — would violate the essential/best-effort distinction the chapter says has to be made explicitly, per endpoint, rather than by default.

## Coding exercise — Model answer

The bug is exactly the failure mode the chapter names first: **"Retrying non-idempotent operations: retrying a payment-charge call without an idempotency key... resulting in duplicate charges during exactly the network conditions that make retries tempting."** `call_with_retry` catches `TransientError` and retries up to `max_attempts` times — but nothing about `payment_gateway.charge(order_id=order_id, amount=amount)` tells the payment gateway "this is the same logical charge as the previous attempt, don't charge twice if you already processed it." If the first attempt's charge actually succeeded on the gateway's side but the response was lost (a classic transient-error trigger — the exact scenario retries exist for), the retry will charge the customer a second time.

Fixed version:

```python
async def charge_customer(order_id: str, amount: int):
    idempotency_key = generate_idempotency_key(order_id)

    async def attempt():
        return await payment_gateway.charge(
            order_id=order_id,
            amount=amount,
            idempotency_key=idempotency_key,
        )

    return await call_with_retry(attempt, max_attempts=3, base_delay=0.1)
```

The key fix: `idempotency_key` is generated **once**, outside the `attempt()` closure — before `call_with_retry` starts its retry loop — and the *same* key is passed on every attempt, including retries. This is deliberate: the idempotency key's entire purpose is to let `payment_gateway` recognize "I've already processed this exact logical charge" across multiple physical HTTP/RPC attempts, so the gateway can return the original result instead of charging again. If `generate_idempotency_key` were called *inside* `attempt()` (once per retry) instead, each retry would mint a new key, and the gateway would see three different "first-time" charge requests instead of one logical charge retried three times — reintroducing the exact duplicate-charge bug the key was meant to prevent. Generating it once per logical operation, before entering the retry loop, is what makes the retries actually safe.

## Quiz (self-check) — Answers

1. **False.** A timeout bounds how long a single call is allowed to take; it doesn't prevent the caller from immediately dialing the same struggling dependency again on the very next request, piling up wasted, doomed calls. A circuit breaker tracks failure *rate* across calls and, once a threshold is crossed, stops sending requests entirely for a cooldown — "failing fast instead of piling up slow, doomed calls against a struggling dependency," protecting both the caller's own resources and the callee's ability to recover. They're complementary, not redundant: a timeout bounds one call's worst case; a circuit breaker prevents repeatedly making that same doomed call.
2. `"retryable": false` tells the client, in machine-readable form, "don't retry this — it will fail identically every time." This matters more than inferring retryability from the HTTP status code alone because a single status code (e.g., `4xx`) can cover multiple distinct situations with different retry semantics — putting the signal explicitly in the envelope removes ambiguity and lets client code branch directly on it rather than maintaining its own mapping of "which status codes are retryable in this API."
3. **`CLOSED`** — normal operation, calls pass through. **`OPEN`** — failing fast, calls are rejected immediately with `CircuitOpenError` without even attempting `fn()`. **`HALF_OPEN`** — testing recovery: one (or a small number of) call is allowed through to probe whether the dependency has recovered, determining whether the breaker returns to `CLOSED` or back to `OPEN`.
4. "Every caller to pile up threads/connections waiting on it, exhausting the caller's own resources and turning one service's slowness into a cascading outage" — i.e., the failure of one slow downstream dependency propagates upward and takes down callers that would otherwise be healthy.
5. **False.** They share a root cause (a slow or failing dependency) but operate via different mechanisms at different points: a bulkhead limits how much of the caller's own capacity any single dependency can ever consume, continuously, from the very first call; a circuit breaker stops sending calls to a dependency only after it's crossed a failure threshold. Removing either one leaves a real gap the other doesn't cover — without a bulkhead, a dependency that's merely slow (not yet failing enough to trip a breaker) can still exhaust shared resources; without a breaker, a bulkhead-limited but persistently failing dependency keeps consuming its capped slots on every retry instead of being cut off.
