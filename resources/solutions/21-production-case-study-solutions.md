# Chapter 21: Production Case Study — Solutions

*Corresponds to: [part6-synthesis/21a-production-case-study-exercises.md](../../part6-synthesis/21a-production-case-study-exercises.md)*

## Concept questions — Model answers

1. When DataLoaders are created once per gateway process rather than once per request, a single DataLoader instance — and its internal per-key cache — ends up shared across every request handled by that process for as long as it stays alive, instead of being scoped to just one request's lifetime. Because DataLoaders cache resolved values by key (e.g., an order ID) to batch and dedupe lookups within a request, a process-scoped DataLoader's cache persists across requests from *different users*, so a value fetched (and cached) while resolving user A's request can be served straight out of that stale, shared cache to user B's request for the same key, without re-fetching or re-checking authorization for user B. That's precisely what "leaked cached order data between users" means here. It connects to "Chapter 8's exact warning" because that chapter evidently already documents this exact class of bug — DataLoader instances need request-scoped lifetimes specifically to prevent cross-request cache leakage — and this incident is presented as a case where that documented warning was known but not followed in this particular implementation.

2. The mechanical cause is that the channel used for the inventory-to-warehouse call was created without deadline propagation wired through — meaning inventory's call to warehouse-allocation didn't inherit the remaining time budget from the original orders-to-inventory deadline, and instead ran with no deadline (or its own unrelated one) of its own. As a result, when orders' original 500ms deadline expired and orders gave up and moved on, inventory had no signal that the work it was still doing on behalf of that now-abandoned request was pointless — it kept executing the downstream warehouse call to completion regardless. This wastes capacity specifically during "exactly the traffic spike that caused the original slowness" because that's precisely the moment when the system is already resource-constrained and most needs to shed work that's no longer useful — instead, the missing deadline propagation causes the system to keep spending scarce capacity on doomed work at the worst possible time, compounding the original slowness rather than recovering from it.

3. The service-to-service token authenticates the gateway itself as a trusted internal caller — it proves "this request is legitimately coming from our gateway," not "this request is legitimately allowed to see this specific user's specific order." Those are two different questions. If a subgraph skipped per-field authorization on the theory that "the gateway already checked the session," it would be conflating caller authentication (is this a legitimate internal service talking to me) with end-user authorization (is this particular end user, whose identity is only available via claims embedded in the forwarded context, entitled to this particular field/record). Skipping the per-field check would mean any query the gateway forwards — regardless of which end user originally issued it — would be treated as fully authorized at the subgraph, which defeats the purpose of having per-user access control at all; the gateway's session validity check only proves someone is logged in, not that they're allowed to see this specific order.

4. The mechanism is gRPC-JSON transcoding (Chapter 14): the REST API is generated directly from the same `.proto` definitions used by the internal gRPC services, annotated with HTTP mappings, rather than being a separately hand-written REST API that happens to sit in front of the same backend. Because both the REST surface and the internal gRPC contract are generated from one shared source of truth, a change to the `.proto` file automatically updates both — there is no second artifact for an engineer to remember to update in parallel, which is exactly the failure mode a hand-maintained REST API alongside a separate gRPC service is exposed to (someone changes the gRPC contract, forgets or delays updating the separately maintained REST layer, and the two silently diverge).

## Design question — Model answer

**Prediction:** during a traffic spike, some fraction of customer-profile-to-billing calls will run long enough that customer-profile's own upstream deadline expires and customer-profile gives up on the request and returns/aborts. Because the channel to billing wasn't wired with deadline propagation, billing has no idea customer-profile's caller has already abandoned the request, and billing keeps executing the (now-pointless) work to completion — exactly the pattern described in the postmortem, just one hop over: capacity gets spent on work whose result nobody is waiting for anymore, at precisely the moment (a spike) when capacity is scarcest. This risks the same kind of compounding slowdown: billing stays busier than it needs to be, which can make *its* downstream calls or unrelated concurrent requests slower too, worsening the very spike that triggered the problem.

**Checklist item the postmortem produced:** the chapter says this incident became "a checklist item in every new gRPC service's review, not just a one-off patch" — specifically, verifying deadline propagation is wired through for every new inter-service gRPC call, not assuming it happens automatically just because an upstream deadline exists somewhere in the request path.

**What would actually catch it:** since the bug is invisible under normal, non-spiky load (it only manifests when the deadline would actually be exceeded), a manual "did you remember" code-review checklist item is necessary but not sufficient — reviewers won't reliably load-test every new call path under simulated spike conditions. A more reliable enforcement mechanism would be: (a) a lint/static-check or a shared internal channel-construction helper that fails a build or CI check if a new gRPC channel is created without explicit deadline/context propagation from the caller's incoming context (making the safe path the only path, rather than relying on each engineer remembering), and (b) a chaos/load test in CI or staging that deliberately induces the exact spike condition (slow the deepest downstream call, verify upstream timeouts propagate and abandoned work is actually cancelled) — connecting back to Chapter 18's point that load testing needs to exercise realistic, not just happy-path, conditions to catch exactly this class of bug before production does.

## Applied exercise — Model answer

**Where it fits:** none of the three existing layers is a clean fit as-is. The gRPC-internal layer is designed for point-to-point service-to-service calls with tight latency budgets and deadline propagation between services that trust each other completely — not for a bulk, cross-service, near-real-time *read* fan-out pattern initiated by a system outside the core order/inventory/customer/billing service group. The federated GraphQL layer is designed around a small number of first-party client teams issuing bounded, per-request queries shaped for UI rendering, with query-cost limiting calibrated against that traffic pattern — a bulk "every order updated in the last 5 minutes, joined with customer tier" query is exactly the kind of expensive, high-fan-out query the existing cost-limiting was calibrated to guard *against*, not accommodate. The REST-via-transcoding layer is built for external, uncoordinated third parties with quota-based per-key rate limiting — a poor fit for an internal system needing frequent, large, low-latency reads.

The better answer is a **new, purpose-built layer**: a dedicated internal read path (e.g., a change-data-capture/event stream from each service, or a periodically refreshed internal read replica/materialized view assembled specifically for analytics) that the BI system consumes directly, rather than issuing live queries against any of the three existing consumer-facing layers. This follows the chapter's own reasoning by symmetry: each existing layer earns its shape from a specific combination of client count, coordination ability, latency needs, and access-pattern shape, and analytics' combination (one internal, coordinated consumer; not latency-sensitive to the same degree as user-facing traffic; bulk/cross-entity access pattern rather than per-entity) doesn't match any of the three existing profiles — it matches none of them well enough to justify bending an existing layer instead of building the right-shaped one.

**New failure mode, by analogy to the postmortems:** by analogy to the DataLoader lifetime bug (a caching/lifetime scope mismatch that leaked data across requests), a bulk cross-service read path risks its own lifetime/scope bug — e.g., a shared connection, cursor, or cache used to assemble the joined "orders + customer tier" result being reused across different analytics query invocations in a way that mixes stale data from one snapshot with fresh data from another, producing a join that's internally inconsistent even though each individual field is technically correct at *some* point in time. The guardrail: make each bulk query's read path explicitly snapshot-scoped (a single consistent point-in-time view assembled per query invocation, not a long-lived shared cache reused across invocations) — the same fix-shape as the DataLoader bug (request-scoped rather than process-scoped state), applied to this new access pattern before it ships rather than after an incident forces the fix, which is precisely the discipline the chapter's closing section says this platform's actual engineering maturity consists of.
