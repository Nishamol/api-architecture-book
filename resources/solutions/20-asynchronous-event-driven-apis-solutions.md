# Chapter 20: Asynchronous and Event-Driven APIs — Solutions

## Concept questions — Model answers

1. Following the flowchart: a single caller *is* waiting for the result (the form submitter wants a decision), so we go down the "Yes" branch to "Can the caller receive an HTTP callback?" The caller is a browser, not a server, so the answer is "No," and the chapter lands on **`202 Accepted` + poll a job resource**: the `POST` returns a `job_id` and a `Location: /jobs/{id}`, and the front-end polls `GET /jobs/{id}` (respecting `Retry-After`) until `status` is terminal. The "202 + webhook" branch is ruled out because a webhook delivery is an inbound HTTP `POST` to a URL the consumer operates — a browser has no addressable, authenticated endpoint to receive that call, and even if it did, the page may have been closed by the time the result is ready. Polling puts the resumption logic on the client that's actually able to hold it.

2. The three things are: (1) at-least-once delivery from the broker, (2) idempotent processing in the consumer (deduping on a stable `event_id` or applying effects in a way that's safe to repeat), and (3) transactional offset commits so the consumer's "I processed up to here" position moves atomically with the effect of processing. The broker can't provide (2) because idempotency is a property of what the consumer *does* with the message — only the consumer knows whether "apply this" is a set operation or an increment. It can't fully provide (3) either, because the effect usually lands in the consumer's *own* database, not the broker, so the atomic unit has to be "apply effect + record progress" in that database, which is outside the broker's control. The broker only owns delivery; "exactly-once" is the name for the whole assembled system behaving as if each message landed once.

3. The dual-write problem: a service needs to change its own state *and* tell the outside world, and those are two separate systems (a database and a message broker) with no shared transaction. If the process crashes, or the publish call fails, after the database commit but before the event is on the broker, the service's state and everyone else's view of it diverge permanently, and nothing logs an error. The transactional outbox eliminates it by making the "tell the outside world" step a row written into an `outbox` table *in the same local database transaction* as the state change — so either both the `UPDATE` and the `INSERT INTO outbox` commit or neither does; there is no partial outcome. A separate relay then reads committed outbox rows and publishes them, retrying safely because consumers dedupe on `event_id`. The original `UPDATE` + `publish` wasn't safe together because the two writes went to two systems with independent failure; the `UPDATE` + `INSERT` is safe because both go to the same transactional database.

4. The failure loop: (1) the receiver gets a delivery and starts its real processing (a DB write, a downstream call) before responding; (2) the backend is slow, so processing takes longer than the sender's delivery timeout (e.g. 5s); (3) the sender's HTTP call times out and it records the delivery as failed; (4) the sender schedules a retry with backoff; (5) meanwhile the receiver's first attempt *finishes successfully* a few seconds later — the work is done; (6) the retry arrives and, if the receiver isn't deduping on `event_id`, the work is done a second time. It compounds because the trigger is backend slowness, and backend slowness correlates with load — so precisely when the system is under pressure, every delivery generates a retry and a duplicate unit of work, adding load. Acking fast (verify, dedupe, enqueue, return `200`) breaks the loop: the sender sees success on the first try and never retries.

## Design question — Model answer

- **Event published:** `payment.settled`, envelope `{event_id, occurred_at, schema_version, payment_id, order_id, customer_id, amount, currency}`. `event_id` is a fresh UUID per event (the dedupe key for all consumers); `occurred_at` plus `payment_id` lets consumers reorder and dedupe. No PII beyond ids that consumers can resolve against their own or the payments service's API.
- **Dual write:** transactional outbox. In the settlement transaction, `UPDATE payments SET status='settled'` and `INSERT INTO outbox (id, topic, payload)` commit together. A relay (poller or CDC connector on the WAL) publishes outbox rows to `payment.settled` at least once. The settlement handler no longer calls the broker directly.
- **Stays synchronous:** none of the four. Marking the order paid is arguably the most coupled, but the order service already reacts to `payment.settled` and owns its own state — making it a synchronous call from `payments` would recreate exactly the cross-service coupling and failure propagation we're removing (an order-service blip would fail settlement). Email, analytics, and fraud re-scoring are all clearly independent reactions. All four become consumers of `payment.settled`.
- **Receipt-email idempotency:** the email consumer keeps an `inbox` / processed-events table keyed by `event_id`, and in one transaction it records `event_id` *and* the fact that a receipt for this `payment_id` was sent (or enqueued to the email provider with an idempotency key of its own). A redelivery finds the `event_id` already recorded and returns without sending. Belt and suspenders: pass `payment_id` as the idempotency key to the email provider so even a bug in the inbox check can't produce two sends.
- **Saga compensation:** if "charge payment" itself were one step of an in-settlement saga (reserve inventory → charge payment → book shipping), and shipping booking failed, the compensating action for the completed charge step would be to issue a **refund** (not delete the charge — you compensate forward with a new offsetting transaction), and the compensating action for the inventory step would be to **release the reservation**. As downstream reactions to an already-settled payment, none of the four need compensation, because the payment is a completed fact by the time they run.

## Applied exercise — Model answer

**1. Replay guard:**

```python
ts = request.headers.get("Webhook-Timestamp", "")
if not ts.isdigit() or abs(time.time() - int(ts)) > 300:
    raise HTTPException(401, "stale or missing timestamp")
```

The timestamp must be *inside* the HMAC (the sender computes the MAC over `f"{ts}.".encode() + body`, and the receiver recomputes it the same way) because a value that's only sent alongside the signature is attacker-controlled: an attacker who captures one valid delivery could replay the exact body with a fresh timestamp header and it would pass a naive "is the timestamp recent?" check. Binding the timestamp into the signed material means changing it invalidates the MAC, so a replay is only possible within the tolerance window *and* only with the original timestamp — which the window then rejects.

**2. Dedupe store challenges:**

- **(a) Per-process set across three replicas:** each replica has its own `set`, so a delivery handled by replica 1 leaves replicas 2 and 3 unaware. When the sender retries (or the load balancer routes a duplicate delivery elsewhere), a different replica sees an `event_id` it has no record of, treats it as new, and processes it again. The concrete scenario: attempt 1 → replica 1 processes and acks slowly; sender times out and retries; attempt 2 → replica 2, which has never seen this `event_id`, processes it → duplicate side effect. The dedupe store has to be shared (Redis/DB) so all replicas consult the same record.
- **(b) TTL shorter than the retry window:** the sender retries over, say, 24 hours, but the dedupe entry expires after 1 hour. A delivery that succeeds on attempt 1 has its `event_id` recorded, but if a late retry arrives at hour 2 (sender's earlier attempts were themselves timing out and backing off), the entry is already gone, the receiver treats it as new, and processes it again. The TTL must be at least as long as the sender's maximum total retry window, plus a margin.

## Quiz (self-check) — Answers

1. **False.** The work isn't done when the response is sent, so `200 OK` misrepresents the outcome. The correct code is **`202 Accepted`** ("request accepted, processing not complete"), with a `Location` header pointing at a job resource the client can poll.
2. **Per-partition.** Kafka guarantees order only within a single partition, not across a topic or globally. The practical consequence: you must choose the message key so that all events that need a relative order (e.g. all events for one order id) hash to the same partition — key by aggregate id, not randomly, or you lose the ordering you need.
3. The producer should **dead-letter the outstanding deliveries and disable the subscription, alerting its owner.** "Keep retrying" is wrong because a permanently-dead endpoint will never succeed, so infinite retries just burn delivery-worker capacity and backlog depth indefinitely, which delays and degrades delivery to *healthy* subscribers sharing that infrastructure.
4. The **inbox / idempotent consumer** pattern. It records each processed `event_id` in the **same database transaction** that applies the message's effect, so a redelivered message finds its `event_id` already present and becomes a no-op.
5. The **trace context** (the `traceparent` value) must be attached as a message header on publish and restored as the span's parent context on consume. Without that, the producer's trace and the consumer's trace are separate traces with no link, and the queue hop shows up as the end of one trace and the unexplained start of another.
